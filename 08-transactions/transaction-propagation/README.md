# Transaction Propagation

Spring transaction propagation defines how a transactional method behaves when it is called while another transaction is already active.

This example demonstrates two commonly used propagation modes:

- `Propagation.REQUIRED`
- `Propagation.REQUIRES_NEW`

It uses a simple Spring JDBC application with an embedded H2 database so that the transaction behavior can be observed directly.

---

## Learning Objectives

By the end of this example, you will understand:

- What transaction propagation means.
- How `Propagation.REQUIRED` behaves.
- How `Propagation.REQUIRES_NEW` behaves.
- The difference between joining an existing transaction and creating a new transaction.
- How transaction rollback affects nested operations.
- How Spring suspends an existing transaction when using `REQUIRES_NEW`.
- Why transactional methods should be called through Spring-managed beans.
- How Spring's transaction management builds on its proxy-based AOP infrastructure.
- How to test transaction propagation using database state.

# What Is Transaction Propagation?

Transaction propagation defines how a transactional method should behave when it is called from another transactional method.

For example:

```text
Outer transaction
       ↓
   Service A
       ↓
   Service B
```

If both methods are transactional, Spring needs to determine whether `Service B` should:

- Join the existing transaction.
- Create a new transaction.
- Execute without a transaction.
- Or use another propagation strategy.

This behavior is controlled using:

```java
@Transactional(propagation = ...)
```

---

# The Two Propagation Modes

This example focuses on:

```java
Propagation.REQUIRED
```

and:

```java
Propagation.REQUIRES_NEW
```

They have an important difference.

### `REQUIRED`

`REQUIRED` joins an existing transaction if one exists.

If no transaction exists, Spring creates one.

Conceptually:

```text
Existing transaction
        ↓
     REQUIRED
        ↓
Join existing transaction
```

### `REQUIRES_NEW`

`REQUIRES_NEW` always creates a new transaction.

If another transaction is already active, Spring suspends it while the new transaction executes.

Conceptually:

```text
Existing transaction
        ↓
   REQUIRES_NEW
        ↓
Suspend existing transaction
        ↓
Create new transaction
        ↓
Execute operation
        ↓
Commit / rollback
        ↓
Resume existing transaction
```

# Database Schema

The example uses two tables:

```sql
CREATE TABLE greetings (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    message VARCHAR(255) NOT NULL
);

CREATE TABLE audit_log (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    message VARCHAR(255) NOT NULL
);
```

The `greetings` table stores the primary operation.

The `audit_log` table stores an audit entry.

This allows us to observe whether each operation was committed or rolled back.

# Configuration

Spring needs a `DataSource`, `JdbcTemplate`, and transaction manager.

## `AppConfig`

```java
@Configuration
@ComponentScan
@EnableTransactionManagement
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        return new EmbeddedDatabaseBuilder().setType(EmbeddedDatabaseType.H2).addScript("schema.sql").build();
    }

    @Bean
    public JdbcTemplate jdbcTemplate(DataSource dataSource) {
        return new JdbcTemplate(dataSource);
    }

    @Bean
    public PlatformTransactionManager transactionManager(DataSource dataSource) {
        return new DataSourceTransactionManager(dataSource);
    }
}
```

---

# `@EnableTransactionManagement`

The:

```java
@EnableTransactionManagement
```

annotation enables Spring's annotation-driven transaction management.

Without it, annotations such as:

```java
@Transactional
```

would not cause Spring to create the transactional proxy required to manage the transaction.

Conceptually:

```text
@EnableTransactionManagement
          ↓
Spring transaction infrastructure
          ↓
Transactional proxy
          ↓
@Transactional method
```

This connects directly to the proxy concepts explored in the Spring AOP module.

# Greeting Repository

The repository stores greetings in the database.

## `GreetingRepository`

```java
@Repository
public class GreetingRepository {

    private final JdbcTemplate jdbcTemplate;

    public GreetingRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public void save(String greeting) {
        jdbcTemplate.update("INSERT INTO greetings (message) VALUES (?)", greeting);
    }

    public int count() {
        Integer count = jdbcTemplate.queryForObject("SELECT COUNT(*) FROM greetings", Integer.class);

        return count != null ? count : 0;
    }
}
```

The repository does not manage transactions itself.

Transaction boundaries are defined at the service layer.

---

public class AuditRepository {

# Audit Service

The `AuditService` demonstrates the two propagation modes.

## `AuditService`

```java
@Service
public class AuditService {

    private final AuditRepository auditRepository;

    public AuditService(AuditRepository auditRepository) {
        this.auditRepository = auditRepository;
    }

    @Transactional(propagation = Propagation.REQUIRED)
    public void saveWithRequired(String message) {
        auditRepository.save(message);
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveWithRequiresNew(String message) {
        auditRepository.save(message);
    }

    public int count() {
        return auditRepository.count();
    }
}
```

---

# `Propagation.REQUIRED`

The first method uses:

```java
@Transactional(propagation = Propagation.REQUIRED)
```

`REQUIRED` is the default propagation mode for `@Transactional`.

When `saveWithRequired()` is called from an existing transaction, it participates in that transaction.

The structure is:

```text
GreetingService transaction
        ↓
save greeting
        ↓
AuditService.saveWithRequired()
        ↓
same transaction
        ↓
save audit
```

If the outer transaction rolls back, the audit operation rolls back with it.

---

# `Propagation.REQUIRES_NEW`

The second method uses:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
```

This tells Spring to create a new transaction for the method.

If another transaction is already active, Spring suspends it.

The structure becomes:

```text
Outer transaction
       ↓
save greeting
       ↓
Suspend outer transaction
       ↓
New transaction
       ↓
save audit
       ↓
Commit new transaction
       ↓
Resume outer transaction
       ↓
Outer transaction fails
       ↓
Rollback outer transaction
```

The audit record can therefore remain committed even though the outer operation fails.

# Greeting Service

The `GreetingService` represents the outer transaction.

## `GreetingService`

```java
@Service
public class GreetingService {

    private final GreetingRepository greetingRepository;
    
    private final AuditService auditService;

    public GreetingService(GreetingRepository greetingRepository, AuditService auditService) {
        this.greetingRepository = greetingRepository;
        this.auditService = auditService;
    }

    @Transactional
    public void saveWithRequiredAudit(String greeting) {
        greetingRepository.save(greeting);
        auditService.saveWithRequired("Saved greeting: " + greeting);

        throw new RuntimeException("Simulated failure");
    }

    @Transactional
    public void saveWithRequiresNewAudit(String greeting) {
        greetingRepository.save(greeting);
        auditService.saveWithRequiresNew("Saved greeting: " + greeting);

        throw new RuntimeException("Simulated failure");
    }

    public int countGreetings() {
        return greetingRepository.count();
    }

    public int countAuditEntries() {
        return auditService.count();
    }
}
```

The exception is intentional.

It allows us to observe what happens to each transaction when the outer transaction fails.

---

# `REQUIRED` Transaction Flow

When:

```java
greetingService.saveWithRequiredAudit("Hello, Spring!");
```

is called, Spring creates an outer transaction.

The greeting is saved:

```text
Transaction A
    ↓
Save greeting
```

Then:

```java
auditService.saveWithRequired(...)
```

is called.

Because the audit method uses `REQUIRED`, it joins the existing transaction:

```text
Transaction A
    ├── Save greeting
    │
    └── Save audit
```

The method then throws:

```java

throw new RuntimeException("Simulated failure");

```

Spring rolls back the transaction:

```text
Transaction A
    ↓
Exception
    ↓
Rollback
    ↓
Greeting removed
Audit removed
```

The final database state is:

```text
Greetings:     0
Audit entries: 0
```

---

# `REQUIRES_NEW` Transaction Flow

Now consider:

```java
greetingService.saveWithRequiresNewAudit("Hello, Spring!");
```

The outer transaction starts:

```text
Transaction A
    ↓
Save greeting
```

Then:

```java
auditService.saveWithRequiresNew(...)
```

is called.

Because the audit method uses:

```java
Propagation.REQUIRES_NEW
```

Spring suspends the outer transaction and creates a new one:

```text
Transaction A
    ↓
Save greeting
    ↓
Suspend Transaction A
    ↓
Transaction B
    ↓
Save audit
    ↓
Commit Transaction B
    ↓
Resume Transaction A
```

The outer method then throws:

```java
throw new RuntimeException("Simulated failure");
```

Transaction A rolls back:

```text
Transaction A
    ↓
Rollback
    ↓
Greeting removed
```

But Transaction B has already committed:

```text
Transaction B
    ↓
Already committed
    ↓
Audit remains
```

The final database state is:

```text
Greetings:     0
Audit entries: 1
```

# Main

The `Main` class demonstrates both scenarios.

```java
public class Main {

    public static void main(String[] args) {

        try (AnnotationConfigApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class)) {
            GreetingService greetingService = context.getBean(GreetingService.class);

            System.out.println("=== REQUIRED ===");

            // Both operations share the same transaction.
            try {
                greetingService.saveWithRequiredAudit("Hello, Spring!");
            } catch (RuntimeException e) {
                System.out.println("Transaction failed: " + e.getMessage());
            }

            System.out.println("Greetings: " + greetingService.countGreetings());
            System.out.println("Audit entries: " + greetingService.countAuditEntries());
            System.out.println();
            System.out.println("=== REQUIRES_NEW ===");

            // The audit operation runs in its own transaction.
            try {
                greetingService.saveWithRequiresNewAudit("Hello, Spring!");
            } catch (RuntimeException e) {
                System.out.println("Transaction failed: " + e.getMessage());
            }

            System.out.println("Greetings: " + greetingService.countGreetings());
            System.out.println("Audit entries: " + greetingService.countAuditEntries());
        }
    }
}
```

Expected output:

```text
=== REQUIRED ===
Transaction failed: Simulated failure
Greetings: 0
Audit entries: 0

=== REQUIRES_NEW ===
Transaction failed: Simulated failure
Greetings: 0
Audit entries: 1
```

# Why Is `AuditService` a Separate Bean?

There is an important Spring AOP detail in this example.

The following approach should be avoided:

```java
@Service
public class GreetingService {

    @Transactional
    public void outer() {
        inner();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void inner() {
    }
}
```

The call:

```java
inner();
```

is a self-invocation.

It does not pass through the Spring proxy, so Spring's transactional interceptor does not get an opportunity to apply the `REQUIRES_NEW` behavior.

Instead, this example uses:

```text
GreetingService
       ↓
AuditService
```

Both are Spring-managed beans.

The call therefore goes through Spring's proxy infrastructure:

```text
GreetingService proxy
        ↓
GreetingService
        ↓
AuditService proxy
        ↓
AuditService
```

This allows Spring to apply the appropriate transaction propagation behavior.

# Connection to Spring AOP

Transaction management is closely related to the Spring AOP concepts explored in the previous module.

Conceptually:

```text
Caller
  ↓
Spring Proxy
  ↓
Transactional Interceptor
  ↓
Target Method
```

For this example:

```text
GreetingService
       ↓
@Transactional
       ↓
Spring proxy
       ↓
Transaction begins
       ↓
AuditService
       ↓
Transactional proxy
       ↓
REQUIRED / REQUIRES_NEW
```

This is one reason understanding Spring AOP is useful when learning Spring transactions.

The transaction behavior is not implemented directly inside the service method.

Spring applies it around the method invocation.

# `REQUIRED` vs `REQUIRES_NEW`

| Feature | `REQUIRED` | `REQUIRES_NEW` |
|---|---|---|
| Existing transaction | Joins it | Suspends it |
| New transaction | Only if none exists | Always |
| Independent commit | No | Yes |
| Independent rollback | No | Yes |
| Outer rollback affects inner operation | Yes | No |
| Uses a separate transaction | No | Yes |

---

# When Should `REQUIRES_NEW` Be Used?

`REQUIRES_NEW` can be useful when an operation should have an independent transaction.

For example:

```text
Main business transaction
        ↓
Process order
        ↓
Write audit record
```

If the audit record must survive even when the main operation fails, an independent transaction may be appropriate:

```text
Main transaction
        ↓
Order processing
        ↓
Failure
        ↓
Rollback

Independent audit transaction
        ↓
Audit record
        ↓
Commit
```

However, `REQUIRES_NEW` should not be used automatically.

Independent transactions introduce additional considerations such as database connections and transaction boundaries.

---

# Important Consideration: Connection Usage

`REQUIRES_NEW` requires a separate physical transaction.

When an existing transaction is suspended, the new transaction may need another database connection.

Conceptually:

```text
Outer transaction
    ↓
Connection A

REQUIRES_NEW
    ↓
Connection B
```

If a large number of transactions use `REQUIRES_NEW` concurrently, the connection pool needs to be configured appropriately.

This is one reason transaction propagation should be chosen based on the application's actual requirements rather than simply using `REQUIRES_NEW` whenever independent behavior sounds useful.

---

# Key Takeaways

- Transaction propagation determines how transactional methods interact with existing transactions.
- `Propagation.REQUIRED` joins the current transaction when one exists.
- `Propagation.REQUIRED` is the default propagation mode.
- `Propagation.REQUIRES_NEW` always creates a new transaction.
- `REQUIRES_NEW` suspends the existing transaction while the new transaction executes.
- A `REQUIRED` operation rolls back with the outer transaction.
- A successfully committed `REQUIRES_NEW` operation can survive an outer transaction rollback.
- Spring applies transaction behavior through proxy-based infrastructure.
- Self-invocation can prevent transactional advice from being applied.
- Separating transactional operations into Spring-managed beans allows the proxy infrastructure to intercept the calls.
- `REQUIRES_NEW` should be used deliberately because it creates an independent transaction and can require additional database resources.
